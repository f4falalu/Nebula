# Deploying Nebula V2 on Render

You need three accounts: **Render** (hosting), **Clerk** (sign-in) and **OpenRouter** (document reading). Nothing needs to be installed on your computer.

Plan and pricing names below were written without access to Render's or Clerk's current docs. If a screen looks different, follow the screen.

## 1. Clerk (sign-in), about 5 minutes

1. Create an application at clerk.com. Turn on **Email** sign-in (add Google if you want it).
2. Open **API keys** and keep this page open. You need the **Publishable key** (`pk_test_…`) and the **Secret key** (`sk_test_…`).
3. Optional but recommended: in **Restrictions**, set sign-up mode to **Restricted** or add an allowlist of your organisation's email domain. Nebula also keeps every new account **pending** until an Administrator activates it, so a stranger who signs up sees nothing.

Use the **development** keys (`pk_test_…`) for the pilot. Clerk's production keys need your own domain (for example `nebula.yourorg.org`) with DNS records. Switch when you add a custom domain.

## 2. Render, about 10 minutes

1. Sign in at render.com with GitHub and allow access to the `nebula` repository.
2. **New → Blueprint**, choose the `nebula` repository. Render reads `render.yaml` and proposes:
   - **nebula**: web service (Starter plan) with a 10 GB disk for documents
   - **nebula-db**: PostgreSQL 16 (basic plan)
3. Fill in the variables Render asks for:
   - `CLERK_PUBLISHABLE_KEY`: the `pk_test_…` key
   - `CLERK_SECRET_KEY`: the `sk_test_…` key
   - `ADMIN_EMAILS`: your email address (comma-separate several). These people become Administrators when they first sign in.
   - `PUBLIC_URL`: leave empty for now
4. Click **Apply**. The first build takes a few minutes. When it's live, Render shows the address, for example `https://nebula-xxxx.onrender.com`.
5. Put that address in `PUBLIC_URL` (Environment tab) and save. Render redeploys.

`NEBULA_SECRET_KEY` is generated by Render. **Don't change it**: it encrypts the stored OpenRouter key and signs document links.

## 3. First sign-in and setup

1. Open the Render address and sign up with an email listed in `ADMIN_EMAILS`. You land in Nebula as an Administrator.
2. **Administration → Setup**: load the starter master data, then edit facilities and items (CSV paste import is available).
3. **Administration → Document reading (AI)**:
   - Create a key at openrouter.ai (Keys) and buy credits (Credits).
   - Paste the key, choose the model, and press **Test connection**.
   - Set the monthly budget and per-user limits, then switch reading on.
4. Invite your team: they sign up at the same address and appear in **Administration → Users & roles** as *pending*. Give each a role (Requisition Assistant, Supervisor or Administrator) and activate them.

## Costs to expect

- Render: the Starter web service, the disk, and the basic PostgreSQL plan are paid monthly; see Render's pricing page.
- OpenRouter: pay as you go for document reading; the monthly budget in Nebula caps it.
- Clerk: free for small teams on development keys.

## Updating

Every push to `main` on GitHub redeploys automatically. Database changes are applied on start-up from `backend/migrations/`.

## Backups

Render backs up paid PostgreSQL plans daily, and snapshots the disk. Test a restore into a separate database at least monthly. You can also export requisitions as CSV from the Requisitions page.

## Running locally (developers)

```bash
cd backend && python3 -m venv .venv && . .venv/bin/activate && pip install -r requirements.txt -r requirements-dev.txt
```

```bash
cd app && npm ci && npm run build:web
```

```bash
cd backend && NEBULA_ENV=development NEBULA_SECRET_KEY=dev DATABASE_URL=postgresql://localhost/nebula STORAGE_DIR=./files uvicorn app.main:app --reload
```

With `NEBULA_ENV=development` and no Clerk key, the sign-in page offers a development sign-in (email and role). Never set `NEBULA_ENV=development` on Render.

Tests: `python -m pytest -q` in `backend/` (needs a local PostgreSQL), and `npm test` in `app/`.
