# Nebula V1: how it maps to the PRD

V1 is a working version of the PRD (`docs/PRD.md`, v2.0) hosted as a claude.ai artifact so it can be shared for feedback without servers or accounts. V2 moves to the PRD's target architecture (React PWA, FastAPI, PostgreSQL, Cloudflare R2).

## What V1 runs on

| PRD component | V1 | V2 |
|---|---|---|
| React + TypeScript PWA | React 18 + TypeScript, built into one HTML page (`app/dist/nebula.html`) | Same code, served from Cloudflare Pages |
| FastAPI API | `app/src/data/services.ts` (every write goes through it) | FastAPI endpoints with the same rules |
| PostgreSQL | claude.ai artifact database (`db` capability), one document per requisition | PostgreSQL schema from PRD §31 |
| Cloudflare R2 | claude.ai artifact assets (`assets` capability) | R2 with signed URLs |
| OCR worker | Claude reads the photos in the viewer's browser (`sample` capability) | Background worker with a chosen OCR/LLM model |
| Clerk authentication | claude.ai sign-in (`user` capability) | Clerk |

## Roles in V1

The artifact's share level is the ceiling:

| Share level | Nebula role |
|---|---|
| Owner, Editor | Administrator |
| Contributor | Requisition Assistant |
| Viewer, Commenter | Supervisor (view only) |

An Administrator can lower a Contributor to Supervisor and give that Supervisor explicit grants (reopen, approve edit requests, download documents) in Administration → Users & roles. Write access to master data, settings and roles is enforced by the platform's database rules; the rest of the permission matrix (PRD §6.3) is enforced by the app.

## Where V1 differs from the PRD

These are deliberate V1 limits. Each is fixed by the V2 migration.

1. **Database-level enforcement (PRD §31.8).** V1 enforces append-only records, the finalization lock, self-approval and chronology rules in the app's service layer. The platform only enforces who may write master data. A determined user with Contributor access could write to the store directly. V2 puts these rules in PostgreSQL constraints, triggers and privileges.
2. **Audit immutability (PRD §30.3).** Audit entries are only ever added by the app, but the store itself doesn't forbid changes.
3. **Requisition numbers (PRD §9).** The per-day counter uses a short database lease (`acquire`) instead of a transaction. Two people registering at the same moment wait for each other; they can't get the same number.
4. **Document access (PRD §13.4).** Files are served by claude.ai to people the artifact is shared with. There are no separately expiring signed URLs. Downloads go through the viewer's save prompt and are audited.
5. **Uploads by Requisition Assistants** need the platform's "uploads for Contributors" feature. Where it isn't enabled, only Editors can upload; the app says so.
6. **Document reading** runs on the viewer's own Claude account when they register a requisition, and asks their permission the first time. PDFs are rendered to images in the browser first. Raw output is kept on the requisition. The model used is reported as a tier, not a version.
7. **Scale.** Each requisition is one document (up to 256 KB) and the app loads all requisitions to calculate analytics. That suits a pilot of a few thousand requisitions. The artifact database holds at most 25,000 documents.
8. **Backups (PRD §32.5)** aren't automated. Use Export CSV on the Requisitions page for snapshots.
9. **Offline** isn't supported (same as the PRD's MVP).

## Decisions taken where the PRD left a choice

- Official reporting = Finalized and Fulfillment Closed; an "In progress" toggle shows provisional figures.
- Reopened requisitions leave official reporting until finalized again; dashboards say how many.
- Lifecycle stages Received, Entered and Validated are derived from `receivedAt`, `entryAt` and `firstValidatedAt`.
- Chronology is checked at minute precision (the time picker's precision). Administrators can override the "earlier than entry/validation" rule with a reason; future dates and out-of-order stages can't be overridden.
- Suggested matches (facility, items) are never applied automatically. "Confirm exact and alias matches" applies only exact, normalized and approved-alias suggestions, on the RA's click.
- Starter master data: the PRD's 8 programmes, the one facility named in the PRD, and a 42-item starter list of common essential medicines (codes `EML-…`) for Administrators to edit or replace. No unit conversions are pre-approved.

## Project layout

```
app/
  src/domain/   pure rules: types, OFR, lifecycle, records, units, matching, metrics, permissions
  src/data/     store adapter, platform capabilities, services (all writes), file handling, extraction
  src/ui/       shell, shared components, charts, filters, styles
  src/pages/    one file per page; req/ holds the requisition tabs
  test/         vitest unit tests for the domain rules
  e2e/          Playwright smoke test of the built page
  build.mjs     bundles to dist/nebula.html
```

The `domain/` folder has no browser or platform dependencies, so its rules and tests carry straight over to V2 (as TypeScript in the frontend, and as the reference for the Python/SQL implementation).
